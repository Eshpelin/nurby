# MQTT Integration for Nurby — Home Assistant First

## Goal

Point Nurby at an MQTT broker (existing or bundled Mosquitto) and get a first-class Home Assistant integration: Nurby appears in HA as a hub device with per-camera child devices — motion sensors, detection event entities, live snapshot tiles, and detect/record switches — with zero YAML. The design replicates Frigate's MQTT conventions (stable topic contract, availability with LWT, retained state replay, `*/set` + `/state` command pairs) and adds HA MQTT discovery (the Viseron/Scrypted approach) for true out-of-the-box HA.

Research basis: Frigate publishes a documented topic tree (`frigate/available` birth/will, `frigate/events` envelope, per-camera counts/JPEG snapshots, retained `*/state` mirrors) consumed by its HA companion integration; it deliberately does not use HA discovery. Since Nurby has no HA companion integration, we emit HA discovery configs instead (retained, on the hub-device + `via_device` pattern). Library: `aiomqtt` (BSD-3, asyncio-native — Nurby is pure asyncio; Frigate's paho-in-a-thread design is unnecessary here). Inbound Frigate/BlueIris consumption is explicitly out of scope for this plan (seam left via topic-source module).

## User stories (to be written into the design doc)

1. As a Home Assistant user, I enter my broker host/credentials in Nurby settings, and my cameras appear under a "Nurby" device with motion sensors, event entities, camera tiles, and switches — no YAML.
2. As a HA user, when a person is detected at the front door after 22:00, an HA automation sends a rich notification with the snapshot attached and a tap-through to the live view.
3. As a HA user, I flip a switch to pause detection or recordings on a camera; the state is retained, survives restarts, and HA shows the true state after reconnect.
4. As a HA user, availability tracking tells me when Nurby or a camera stream is offline.
5. As a Node-RED / self-hoster, I subscribe to `nurby/#` and build my own automations against a documented, stable topic contract whose event payloads match the existing webhook payloads.
6. As a new self-hoster without a broker, I enable the bundled Mosquitto compose profile and everything works.

## Topic contract (prefix configurable, default `nurby`)

```
nurby/status                                  birth "online" / will "offline" / "stopped" (retained, QoS1)
nurby/stats                                   JSON, every mqtt_stats_interval (default 60s)
nurby/events                                  JSON = existing webhook payload shape (docs/webhooks.md), QoS1, non-retained
nurby/cameras/{slug}/motion                   ON/OFF, non-retained, OFF held via 30s off-delay
nurby/cameras/{slug}/events                   JSON {"event_type": "person", ...} for HA event entity, QoS1
nurby/cameras/{slug}/snapshot                 raw JPEG bytes (event-driven + periodic keyframe, `mqtt_camera_frame_interval` default 10s, 0=off)
nurby/cameras/{slug}/detect/set|state         ON/OFF command + retained state mirror
nurby/cameras/{slug}/recordings/set|state     ON/OFF command + retained state mirror
nurby/cameras/{slug}/snapshots/set|state      ON/OFF command + retained state mirror
homeassistant/<component>/<object_id>/config  HA discovery configs (retained, QoS1; empty payload = remove)
```

Topics use a readable camera name-slug; HA `unique_id`s are derived from the stable camera UUID so entity identity survives renames (discovery is republished with new topics on rename). QoS: telemetry 0–1, state/discovery/availability QoS1 retained.

## HA discovery design

- Hub device published first: identifiers `["nurby"]`, model/manufacturer/sw_version from `VERSION`; then per-camera devices with `via_device: "nurby"` (HA requires hub before children).
- Entities per camera: `binary_sensor` motion (device_class motion), `event` entity (event_types from Nurby labels: person, vehicle, face, plate, …), `camera` entity fed by the snapshot JPEG topic, `switch` × detect/recordings/snapshots (command_topic → `/set`, state_topic → `/state`).
- Global: `sensor` with `json_attributes_topic` on `nurby/stats`.
- All entities share `availability_topic: nurby/status` (payload_available `online` / not_available `offline`).
- HA-restart coordination: subscribe `homeassistant/status`; on `online`, republish all discovery configs + retained states (ESPHome pattern).
- Removal: empty payload published to config topics when the integration is disabled or a camera is deleted.

## Architecture

One MQTT client, hosted as a supervisor in the **API process** (mirrors `TelegramPollerManager`: started in the `services/api/main.py` lifespan, `stop()` + task cancel on shutdown). Every process can emit MQTT messages through a small Redis pub/sub bus — `shared/mqtt_bus.py` exposing `mqtt_publish(topic, payload, retain)` that publishes to a new `nurby:mqtt:out` channel; the bridge drains it and forwards to the broker (this mirrors how `fire_actions` already reaches the WS relay via `nurby:ws:broadcast`).

New module `services/integrations/mqtt/` (runtime code must live under `services*`/`shared*` — `integrations/` at repo root is not packaged):
- `topics.py` — topic name builders, slug handling, constants (pure, heavily unit-tested)
- `discovery.py` — discovery payload builders (hub-first ordering, removal)
- `client.py` — `MqttBridge` supervisor: aiomqtt connect loop with exponential backoff, will/birth on `nurby/status`, resubscribe on reconnect, retained-state replay after SUBACK, echo filtering on `nurby/#`, drains `nurby:mqtt:out` and inbound commands
- `handlers.py` — command handling: `/set` payloads validated, written to the Camera row in DB, per-camera restart signaled via the existing `nurby:stream_restart:<cam>` Redis key; exact camera toggle columns confirmed against `shared/models/cameras.py` during implementation
- `publishers.py` — event publisher (hook in `services/events/firing.py` `_broadcast_fired`-adjacent: publish full webhook-payload-shaped event to `nurby/events` + per-camera `events` + snapshot JPEG), motion publisher (ingestion `StreamWorker` publishes motion transitions through the bus with off-delay), stats loop (psutil + camera status), snapshot publisher
- Future seam: `sources/` package (empty in this plan) for inbound Frigate/BlueIris parsing profiles

Settings (app-settings layer, `shared/app_settings.py` DEFAULTS + `SETTINGS_WHITELIST` in `services/api/routes/system.py` + `SystemSettingsUpdate` schema): `mqtt_enabled` (false), `mqtt_host`, `mqtt_port` (1883), `mqtt_username`, `mqtt_password` (Fernet-sealed via `shared/camera_secrets`, write-only per the `push_fcm_service_account` precedent), `mqtt_tls` (false), `mqtt_topic_prefix` ("nurby"), `mqtt_client_id` ("nurby"), `mqtt_discovery_enabled` (true), `mqtt_stats_interval` (60), `mqtt_camera_frame_interval` (10).

API: new `services/api/routes/mqtt.py` — `GET /api/integrations/mqtt` (connection state, last error) and `POST /api/integrations/mqtt/test` (connect, return CONNACK result; telegram test-endpoint precedent).

Frontend: `frontend/src/components/MqttSection.tsx` (broker form, enable + discovery toggles, test-connection button, status line), mounted in `frontend/src/app/settings/page.tsx` next to `TelegramSection`.

Dependency: add `aiomqtt>=2.3` to `pyproject.toml` with a comment (BSD-3-Clause).

## Phases

1. **Design doc** — `docs/integrations/mqtt.md`: topic contract, HA entity map, user stories above, config reference, future inbound-seam note.
2. **Foundation** — aiomqtt dep, settings keys + whitelist + schema, `shared/mqtt_bus.py`, `MqttBridge` (connect/LWT/reconnect/resubscribe/replay), routes + `MqttSection.tsx` + test endpoint. Toggle exists end-to-end; nothing published yet.
3. **Telemetry** — event publisher (firing hook), motion publisher (ingestion, off-delay), snapshot publisher (observation-driven + periodic keyframes), stats loop; retained `/state` mirrors of current camera settings.
4. **HA discovery** — `discovery.py`, hub-first publish, `homeassistant/status` re-announce, removal on disable/camera delete; entity set as listed above.
5. **Control** — `/set` handlers → DB writes + stream-restart signals; state mirrors kept authoritative (bridge re-publishes on settings change observed via DB/Redis).
6. **Bundled broker + docs** — optional `eclipse-mosquitto` compose profile (`docker-compose.mqtt.yml` + `config/mosquitto.conf`, 1883), `docs/integrations/home-assistant.md` setup guide with HA notification automation + a shipped notification blueprint YAML, README "Programmable"/structure updates.

## Tests (fast suite, no real broker — mock/asyncio-fake client)

- `tests/test_mqtt_topics.py` — slug stability, topic/payload shapes, envelope fields
- `tests/test_mqtt_discovery.py` — required fields, unique_id derivation, hub-before-children ordering, removal = empty payload
- `tests/test_mqtt_bridge.py` — reconnect/backoff loop, birth/will, echo filter, bus drain, command handler writes setting + emits restart key
- `tests/test_mqtt_routes.py` — status/test endpoints with mocked client
- Extend existing firing test to assert the MQTT bus publish on event fire

## Explicitly out of scope (follow-ups)

Inbound MQTT sources (Frigate events → Nurby observations; BlueIris/Scrypted profiles) — the `sources/` seam and the single shared client make this a natural next plan. A HACS custom HA component (Frigate-style) is likewise a future option; discovery covers HA today.
